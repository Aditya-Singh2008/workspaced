# Phase 4b: Video Viewer Plugin (libmpv Engine)

Depends on Phases 1 through 3 being complete. Independent of Phase 4a (image), the two share nothing beyond the Phase 1 contract.

**This is a revised version of this phase.** The original brief specified the platform's native `<video>` element as the playback engine. That implementation did not meet load-time or playback-smoothness requirements. This version replaces the engine entirely rather than tuning the old one. If Phase 4b was already built against the prior brief, do not work from this file directly — use `04b-refactor-migration.md` instead, which guides the migration from the old implementation to this one.

## Why the native `<video>` element was the wrong foundation

A webview's `<video>` element is a thin wrapper around whatever decode/render pipeline the platform webview ships: WebView2, WKWebView, and webkit2gtk each make different, non-negotiable choices about codec support, hardware-decode fallback behavior, and — critically for smoothness — frame presentation timing. `AGENTS.md`'s Platform targets section already documents one consequence of this (`requestAnimationFrame` does not fire when the window isn't being composited, which pdf.js's render loop depends on); a webview `<video>` element's presentation is subject to the same compositor and main-thread scheduling as everything else in the webview, which is not the guarantee a smooth video player needs. There is no tuning path from "webview video element" to "mpv-grade playback"; they are different architectures. This phase replaces the engine.

## Goal

Video playback built on **libmpv** (the actual mpv media player core, via its C client API), driven from Rust in `src-tauri`, rendered through a native, GPU-composited surface positioned over its tile, not through the webview's own video/canvas pipeline at all. The React-side UI (transport controls, toolbar contributions, keybinds, sidebar entries once annotation-adjacent features exist) stays exactly where it already is; only the decode and render engine underneath it changes. Take mpv itself as the standard to match, not a set of features to reimplement by hand: almost everything in this brief's feature list is a thin binding onto a primitive mpv already has, not new logic to write.

## Foundation: build on `tauri-plugin-libmpv`, verify before committing further

A maintained Tauri plugin already exists for embedding mpv via libmpv (`tauri-plugin-libmpv` / `tauri-plugin-libmpv-api`, distinct from the similarly-named `tauri-plugin-mpv`, which drives an external mpv *process* over JSON IPC and whose own documentation states window embedding does not work there — do not use that one). The libmpv-linked plugin ships a wrapper library plus prebuilt binaries for Windows/macOS/Linux and a JS API shaped almost exactly like what this phase needs: `init`, `destroy`, `command`, `setProperty`, `getProperty`, `observeProperties`.

Verify its current state (release recency, open issues, and specifically anything related to multiple simultaneous embedded instances) before depending on it, since this is a small, single-maintainer project, not a large ecosystem library. Two things it does **not** demonstrate out of the box, and which are this phase's real engineering work:

1. **Multiple simultaneous instances**, one per open video tile, correctly created, hidden, resized, and destroyed as tiles are opened, tabbed away, resized, and closed within the docking layout. Its published examples are a single full-window player.
2. **Position-sync against a docking tile**, not a whole application window.

If prototyping against it reveals it cannot support N independent instances cleanly, fall back to raw FFI bindings generated by `bindgen` against libmpv's own `client.h` (`libmpv2-sys` or `libmpv-sys` as a starting point for the generated bindings, hand-written safe wrappers on top, matching what `tauri-plugin-libmpv` itself does internally) rather than a second, less-maintained wrapper crate. Document whichever path is taken and why, in `src-tauri/video/README.md` or equivalent, the same way `AGENTS.md` documents the pdf.js version pin.

## Architecture: per-platform native surface embedding

The webview renders the UI with a transparent region where video goes; a native surface outside the webview, owned by Rust, renders mpv's actual decoded and scaled frames directly via the platform's GPU API into that region. The three platforms do **not** use the same technique, and picking the wrong one per platform is the most likely way this phase goes sideways.

**Windows.** A sibling native window, positioned and sized via `SetWindowPos`, kept in sync with the video tile's on-screen rect. Win32 supports absolute, client-driven window positioning without restriction, so this is reliable. This is the technique validated in practice (per a real Tauri-plus-libmpv integration report): read the tile's `getBoundingClientRect()` in the frontend on resize/scroll/layout-change, throttle to animation-frame timing, and push the resulting rect to Rust, which repositions the native mpv window to match.

**macOS.** True `NSView` subview embedding into the Tauri window's content view, not a sibling window. This is the same architecture IINA (mpv's own macOS GUI) uses. It sidesteps a specific caveat already observed in practice: the transparent-window-plus-sibling-window trick that works on Windows does not carry over cleanly to macOS's window compositing model. Use `raw-window-handle` to obtain the parent `NSWindow`'s content view and add mpv's rendering view as a subview, positioned via the same rect-sync mechanism as the Windows path, just applied to a subview's frame instead of a sibling window's position.

**Linux.** Neither of the above. Wayland's core protocol does not let a client position its own top-level windows at absolute screen coordinates the way X11 does (positioning is the compositor's job, not the client's), which breaks the sibling-window-sync technique outright on Wayland, not just under some compositors. The reliable path is in-process: render through libmpv's render API (`mpv_render_context`, OpenGL) directly into a `GtkGLArea` living inside webkit2gtk's own GTK widget tree, in the same process, so no window positioning is ever required, the video surface is just another widget in the layout. Verify this against the actual target compositors (GNOME/Mutter, KDE/KWin) since some Wayland compositors implement non-standard positioning extensions that others don't; do not build a solution that only works on one of them without saying so.

## Tasks

**mpv engine integration (`src-tauri/video/`)**

1. Initialize libmpv with hardware decode enabled per platform: `hwdec=auto-safe` as a starting point (safe fallback to software decode if hardware decode isn't available for a given codec/driver combination), and the modern GPU-accelerated video output (`vo=gpu-next` in current mpv versions; verify this is still the current recommended value at implementation time, mpv's defaults do change between releases).
2. Implement per-tile instance lifecycle: create on tile open, hide (not destroy) the native surface and pause the render loop when a tile is tabbed behind another (matching dockview's `defaultRenderer: "always"` — the same "decoders are not thrown away on every tab switch" principle already established for other plugins applies here, just enforced at the native-surface level instead of the DOM level), fully destroy on tile close.
3. Implement the position-sync bridge: frontend reports the tile's screen-space rect on every resize/scroll/layout change (throttled to animation-frame timing, not sent on every pixel of a drag), Rust repositions/resizes the corresponding native surface using the platform-specific technique above.
4. Drive playback through libmpv's own command/property/event API (`observeProperties` for `time-pos`, `duration`, `pause`, etc.), not by reimplementing transport logic by hand. Almost every feature below already exists as an mpv primitive; the work is binding to it correctly, not building it.

**Playback feature set**

All of the following map onto existing mpv/libmpv primitives; treat "does mpv already do this" as the first question for each one before writing custom logic:

1. Transport controls: play/pause, seek, frame-step, variable speed (mpv's `speed` property), J/K/L shuttle and standard shuttle keybinds.
2. Scrubber thumbnail preview.
3. A/B loop points (`ab-loop-a`/`ab-loop-b` properties).
4. Audio track and subtitle/caption track selection, with subtitles rendered through libmpv's native `libass`-based renderer, not a browser `<track>` element — this gets full ASS/SSA styling support essentially for free, a meaningful step up from WebVTT-only rendering.
5. Chapter markers, from mpv's chapter list property.
6. Volume/mute, remembered per session.
7. Frame capture, via mpv's `screenshot-to-file` command or a direct grab from the render surface (pick whichever integrates more cleanly with Phase 4a's image export path, and document the choice); reuse that export path rather than duplicating image-encoding logic.
8. Metadata panel: codec, resolution, framerate, bitrate, duration, container, audio track details, all available as libmpv properties.
9. Picture-in-picture and fullscreen for the focused tile.

## Format and codec coverage

This is now simpler than the original brief, and worth stating plainly: coverage is whatever the bundled FFmpeg (inside libmpv) supports, uniformly across all three platforms, since decode no longer goes through the webview at all. The original concern (H.265/AV1 support varying by WebView2/WKWebView/webkit2gtk) no longer applies to whether a file plays. What still varies per platform is **hardware-decode acceleration** availability (VideoToolbox on macOS, D3D11VA/DXVA2 on Windows, VAAPI on Linux) — `hwdec=auto-safe` handles this gracefully by falling back to software decode rather than failing, so this should never produce a playback failure, only a performance difference worth surfacing in the metadata panel (report whether the active decode path is hardware or software).

## Performance requirements (the actual point of this refactor)

1. Time-to-first-frame from file-open must be measured and reported as part of this phase's verification, not assumed. Establish a concrete target (for example, comparable to opening the same file directly in the standalone mpv player on the same machine, within a small margin for the IPC/embedding overhead) rather than a vague "faster than before."
2. Dropped-frame count during sustained playback of a demanding file (high framerate/resolution, or a codec requiring software decode) must be measured on all three platforms.
3. The decode-and-present loop must never be gated on the webview's `requestAnimationFrame` or main-thread scheduling; presentation timing comes from the native surface's own vsync/present cycle, which is the entire point of moving off the webview `<video>` element.
4. Record both metrics as a documented baseline in this phase's own notes so a future regression is measurable, not just felt.

## Fallback and robustness

If libmpv fails to initialize on a given machine (missing system library where one is required, driver issue, etc.), the plugin must show a clear per-tile error state per the Phase 1 contract's error convention. **Do not silently fall back to a native `<video>` element as a hidden second implementation.** Maintaining two playback engines defeats the purpose of this refactor and doubles the maintenance surface for exactly the class of bug (inconsistent behavior across two code paths) this phase exists to eliminate. A clear failure is the correct fallback, not a degraded second engine.

## Plugin contract implementation

Unchanged from the original brief's intent, now backed by the new engine:

1. **Thumbnail** - capture a representative frame (around 10% into the duration) via the same mechanism as frame capture above.
2. **Search** - not implemented, unless subtitle/caption text is present, in which case search over caption text and jump to the corresponding timestamp via the contract's `reveal` mechanism.
3. **Copy** - frame capture (current frame as image data) via the contract's copy method.
4. **Serialize/restore** - current playback position, volume, selected audio/subtitle track, and active A/B loop points.

## Toolbar contributions and keybinds

Same discipline as every other plugin in this codebase: contribute a minimal, essential-only control set when a video tile is focused (play/pause, seek, volume), everything else keybind- and context-menu-accessible, registered through `viewers/video/actions.ts` following the same single-source-of-truth pattern `viewers/pdf/actions.ts` established. Weigh any new listed keybind row against a small cap the same way the PDF plugin's brief was held to; do not let this plugin's reference-modal section grow into a manual.

## Verification

1. Open one file from each format/codec combination previously specified (MP4, WebM, MOV, MKV, AVI, OGV) on each of the three target platforms; confirm playback, correct hardware-vs-software decode reporting, and no codec-based failures now that decode no longer depends on the webview.
2. Measure and report time-to-first-frame and dropped-frame count per the Performance requirements section, on all three platforms, and compare against the prior native-`<video>` implementation's numbers to demonstrate the refactor actually fixes the reported problem.
3. Open several video tiles simultaneously in different tiling arrangements (split, stacked, tabbed); confirm each has its own correctly positioned, independently controllable native surface, and that tabbing a video tile behind another hides its surface while keeping playback state alive for instant resume.
4. Resize a video tile's pane by dragging a divider; confirm the native surface tracks the resize smoothly, without visible lag or tearing relative to the surrounding UI.
5. Confirm frame-step, variable speed, A/B loop, track selection, chapter navigation, and subtitle rendering (including styled ASS/SSA subtitles, not just plain text) all work correctly.
6. Confirm picture-in-picture and fullscreen enter/exit cleanly without breaking the surrounding tiling layout.
7. Deliberately break libmpv initialization (rename/remove the library dependency in a test build) and confirm the plugin shows a clear per-tile error rather than crashing the shell or silently degrading to a different engine.
8. Confirm session persistence correctly restores playback position, track selection, and loop points, cross-checked against Phase 7.

## Constraints

Do not implement inversion or any PDF/image-specific concept here. Do not maintain the native `<video>` element as a fallback path. Do not attempt Windows/macOS's window- or view-based embedding technique on Linux under Wayland; verify the GtkGLArea in-process approach against real target compositors instead of assuming it behaves like X11. Document the libmpv packaging approach (system dependency vs. bundled wrapper binaries) in `AGENTS.md`'s "Building and releasing" section as part of this phase's own deliverable, per that section's standing instruction to keep itself current as phases land.
